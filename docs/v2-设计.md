# ZRemote v2 设计：桌面直推通知

状态：已实现（v1.2.0 / versionCode 23） · 2026-10-20
分支：`feat/v2-push`

## 0. 一句话

v1 的通知靠手机端 WebView 前台注入（L1）+ 实验性保活（L2，HyperOS 冻结不可靠）+ JobScheduler 周期拉网页（L3，延迟高耗电高）。
v2 改为：**桌面端 watcher 监听 ZCode 客户端本地事件 → 推送 ntfy → 手机端轻量 HTTP 接收（前台流式订阅 + Job 兜底轮询）**，复用 NotifyEngine 既有通知渠道与历史落库；砍掉 L2。

## 1. 事件源调研结论（第一阶段取证）

### 1.1 结论：ZCode 桌面客户端有可编程消费的本地事件源，无需 DOM 监听

桌面客户端把运行时遥测写进两个本机位置（均为用户目录，无加密无锁文件，可直接读）：

**A. 每日 JSONL 运行日志（v2 采用）**
`C:\Users\<user>\.zcode\cli\log\zcode-YYYY-MM-DD.jsonl`（按本地日期滚动，追加写）

核心生命周期事件（`module:"core.runtime"`），全部携带 `sessionId` / `turnId` / `timestamp`：

| event | status | 含义 |
|---|---|---|
| `turn.started` | started | 一轮任务开始（用户发了消息） |
| `turn.completed` | completed | 一轮任务正常结束 |
| `turn.failed` | cancelled | 用户主动取消（不告警） |
| `turn.failed` | failed | 真实错误（模型/网络/运行时） |

实测样本（2026-10-20 日志，节选脱敏）：
```json
{"timestamp":"2026-10-19T19:39:27.657Z","level":"info","event":"turn.completed",
 "module":"core.runtime","sessionId":"sess_62a56810-…","turnId":"turn_ccb7b66e-…",
 "durationMs":51328,"status":"completed","context":{"turnNumber":64,"toolCallCount":0}}
```
状态统计（10-15 至 10-20 五个日志文件）：started 223 / completed 167 / cancelled 41 / failed 13，事件齐全。

**B. SQLite 数据库（标题来源）**
`C:\Users\<user>\.zcode\cli\db\db.sqlite`（WAL 模式，约 78MB）

- `session` 表：`id`（`sess_<uuid>`，与手机端远程控制页任务卡的 `data-testid="task-item-sess_<uuid>"` **同一 ID 空间**）、`title`（默认取用户首条输入）、`task_type`、`parent_id`。
- `message` 表：`data.time.completed` 存在 = 助手回合结束；`data.error` = 出错。**实时性验证**：调研时最后一条 assistant 消息无 `completed`，正是当时正在运行的会话——库是活的。
- 只读连接（`readOnly:true`）在 WAL 下与客户端并发读写无冲突，实测返回秒级新鲜数据。

**过滤规则（实测得出）**：日志里 `turn.*` 事件也会来自 `selection_side_chat`（划词侧聊）和 `subagent_child`（子代理）会话；远程控制页只展示根任务。watcher 只放行 `task_type='interactive' AND parent_id IS NULL` 的会话。抽查 10-20 日志：5 个出现 turn 事件的会话中 4 个是根任务、1 个侧聊，DB 查询 100% 命中标题。

### 1.2 备选方案对比（均已否决，不再实施）

| 方案 | 结论 | 原因 |
|---|---|---|
| 桌面无头浏览器开远程控制页 + DOM 监听（复用 INJECT_JS） | 否决 | 需要 Chrome/Playwright 常驻 + 扫码配对会话（会顶掉手机端"一次只允许一个手机连接"）；维护成本 = 手机端再抄一份且双份脆弱 DOM 依赖 |
| 轮询 db.sqlite message 表 | 备而不用 | 需要自己拼"最后一条消息是否 completed"的状态机，且读大库频繁；日志事件是现成的状态机输出 |
| ZCode 官方 CLI / 通知钩子 | 不存在 | 客户端数据目录内无 hook/插件机制痕迹；无公开文档承诺此类接口 |

### 1.3 风险与边界（必须写明）

- 日志格式是**客户端内部格式，非公开 API**（客户端版本 0.16.9 实测）。官方改版的风险与手机端 INJECT_JS 同级：都靠本文件/脚本集中维护。watcher 对解析失败行逐条容错（跳过不崩）。
- 客户端**未运行**时日志不增长，watcher 空转——天然正确（客户端没跑就没有任务状态变化）。
- WAL 残留 + 客户端崩溃退出后，只读连接可能打开失败：watcher 自动降级 `immutable=1`（牺牲新鲜度换可用性），下轮重试正常打开。

## 2. 数据流

```
ZCode 桌面客户端
  │ 追加写
  ▼
~/.zcode/cli/log/zcode-YYYY-MM-DD.jsonl ──(2s 轮询增量读取)──► 桌面 watcher (tools/zrc-watcher.mjs)
~/.zcode/cli/db/db.sqlite ────────(按需查标题, 只读)──────────►  │
                                                                  │ 过滤: interactive 根会话; cancelled 忽略
                                                                  ▼
                                                     POST {ntfy服务器}/{topic}
                                                      Title=人话  Body=事件JSON  Priority=错误高/完成默认
                                                                  │
                                                  ┌───────────────┴───────────────┐
                                                  ▼                               ▼
                              手机 APP 前台: 流式订阅                手机 APP 被杀: JobScheduler 拉起
                              GET {server}/{topic}/json             SyncJobService → pollOnce()
                              ?since=<水位>  长连接逐行读            (轻量模式: 成功即不拉 WebView)
                                                  └───────────────┬───────────────┘
                                                                  ▼
                                    NtfyReceiver 解析 → NotifyEngine.onTaskEvents()
                                    （沿用 task_done/task_alert 渠道、静默时段、history.json）
                                                                  │
                                                                  ▼
                                              同步更新 last_snapshot（抑制 L3 重复 diff）
```

事件 JSON（ntfy message body，与手机端 L1 事件同构 + 扩展字段）：
```json
{"t":"status","id":"task-item-sess_<uuid>","name":"<会话标题(截断60)>",
 "from":"运行中","to":"已完成","uid":"turn_<id>:completed","dur":51328}
```
`uid` = turnId+终态，全局唯一，供去重；`from` 由 watcher 内存中的会话状态机推出。

## 3. 与 L1 / L3 的去重策略

三个事件源会产生重叠，去重分两层：

1. **手机端 NotifyEngine 时间窗去重**（新增，一处覆盖三源）：事件入历史前，回看最近 50 条，若 `id` 与 `to` 都相同且时间差 < 150s → 丢弃（不记历史不弹通知）。前台 L1 秒级发现 + 直推秒级到达 → 只留一条。
2. **直推写回快照**（新增）：NtfyReceiver 每处理完一批事件，把 `{id: {n,s:to}}` 合并进持久化的 `last_snapshot`。L3 的注入脚本 `loadLast()` 起 diff 时看不到变化 → 不产生重复事件。这解决"150s 窗口外 L3 晚到"的场景（Job 15-60 分钟后才跑）。
3. **L1 不改**：注入脚本与桥零改动，官方改版时维护面不扩大。

去重窗口选 150s 而非更长：任务不可能在无中间态的情况下重复进入同一终态（已完成→运行中→已完成 必有中间事件），更长的窗口反而可能吞掉"错误→(自动重试)→错误"这类真实连续告警。

## 4. 失败重试

**桌面→ntfy**：POST 失败后 3 次退避重试（5s/30s/120s）；仍失败进内存 pending 队列，此后每次新事件或每 5 分钟重 flush。桥重启丢 pending —— 可接受：手机端 L3 仍在，且 ntfy.sh 缓存 12h，手机下次 `since` 拉取不会漏已成功发布的事件。

**手机→ntfy**：前台流断线 15s 退避重连（`since` 带水位，不丢不重）；Job 内 `pollOnce` 失败 → 本次回落到完整 L3 WebView 模式（老路径兜底），水位不推进。

**水位**：手机存最近一条 ntfy 消息的 `time`（epoch 秒）+ `id`，取 `since=<秒>`。首次开启取当前时间（不吃 12h 历史积压）。

## 5. 设置项迁移（砍 L2）

| v1.1.0 | v1.2.0 |
|---|---|
| 设置·通知·「实时模式」开关（KeepAliveService 前台保活） | **删除**。`KeepAliveService.java` 删除、Manifest 移除、`realtime` 偏好清除、`service`（实时模式）通知渠道在 init 时 deleteNotificationChannel 清理 |
| （无） | 设置·通知·新增「**桌面直推**」开关 + 服务器地址 + Topic + 「测试拉取」按钮 + 上次结果行 |
| 兜底检查间隔 15/30/60 分钟 | 增加 120 分钟档（直推开启时建议放宽）；默认仍 30 |

迁移文案（设置页直推开关副标题）：「桌面端实时推送任务状态，取代旧版"实时模式"保活（更省电、更可靠）。需在电脑部署 watcher，见仓库 README·桌面直推一节」。

老用户升级路径：`install -r` 保留数据；若 v1 开着实时模式，升级后保活服务自然消失（类已删），无残留通知；`bootstrap()` 一次性清 `realtime` 键。

## 6. ntfy 选型

**默认公共 ntfy.sh + 随机长 Topic（26+ 字符含 128bit 熵），自建为备选（改服务器地址即可，两端都已参数化）。**

权衡：
- **公共 ntfy.sh**：零运维、免费、12h 消息缓存、限速（约 60 条/小时/visitor，本场景每小时几条，远未触及）。Topic 名即凭据——随机长串不可猜，但**消息内容对 ntfy.sh 运营方可见**（见下）。
- **自建**：数据不出内网/Tailscale；代价是一台常开机器 + 运维。本机电脑会睡眠，不适合当自建服务器；未来若部署 NAS 可平移（手机设置改服务器地址、watcher 改 server 配置，零代码改动）。

**隐私披露（同步进隐私政策与 README）**：直推开启时，任务标题（默认=会话首条输入，截断 60 字）与状态变化经过所选 ntfy 服务器传输；不发送代码、文件与凭据。介意者自建或关闭直推（退回 L1+L3）。

Topic 生成：watcher 端 `zrc-` + 32 hex（crypto 随机）；**绝不入库/入文档**。实际配置存放在仓库之外的用户自有目录（不入任何 git 仓库）。

## 7. 桌面 watcher 部署形态

- 代码：仓库 `tools/zrc-watcher.mjs`（零依赖 Node ≥18，公开可用）。
- 两种运行方式：
  1. **独立**：`node tools/zrc-watcher.mjs --server https://ntfy.sh --topic <t>`（参数或同目录 `zrc-watch.json`）。
  2. **挂进本机常驻桥**（部署细节属个人环境，路径不入库）：动态 import 上述模块，失败不影响桥本体；桥新增端点：
     - `GET /zrc`：watcher 状态（enabled/文件偏移/最近事件/最近推送结果/pending 数；topic 打码只报长度）
     - `POST /zrc/config`：`{enabled?, server?, topic?, generate?}`
     - `POST /zrc/test`：合成一条假完成事件走全链路（唯一 uid，手机端照常去重）
- 桥端点文档追加至 `桥接服务_说明.md`。
